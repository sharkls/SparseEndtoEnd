# FP16 精度优化总结

## 当前状态

经过多轮优化，FP16 精度的成功率已经显著提升：

- **最佳成功率**：100%（在某些运行中）
- **平均成功率**：75%-95%（不同运行间有波动）
- **主要问题**：部分节点在特定样本上仍会产生 NaN

## 已实施的优化

### 1. FP32 输出方案
- **`getOutputDataType`**：在 FP16 输入模式下返回 `DataType::kFLOAT`（FP32）
- **Kernel 实现**：插件内部完全使用 FP32 计算，输出 FP32 值
- **TensorRT 转换**：由 TensorRT 负责 FP32 到 FP16 的最终转换

### 2. 实时 Inf 检查
- **fmaf 累加循环**：在每次 `fmaf` 操作后立即检查 `accum` 值
- **立即 clamp**：如果产生 Inf 或超出安全范围，立即 clamp 到 `[-88, 88]`
- **多重检查**：循环结束后再次检查并 clamp，确保值在安全范围内

### 3. 数值稳定性增强
- **sigmoid_centered**：数值稳定的实现，处理边界情况
- **exp 溢出保护**：限制 `log_size` 到 `[-11, 11]`
- **NaN/Inf 检查**：在所有关键计算步骤添加 `isFinite` 检查

### 4. 输出指针计算修复
- **字节 stride**：正确计算输出指针的字节偏移
- **类型匹配**：正确处理 FP32 输出类型

## 剩余问题

### 1. 成功率波动
- 不同运行间的成功率在 75%-95% 之间波动
- 某些节点在特定样本上偶尔产生 NaN

### 2. 可能的原因
- **TensorRT 引擎缓存**：可能存在缓存不一致
- **CUDA 执行顺序**：并行执行可能导致不确定的结果
- **数值精度边界**：某些极端输入值可能导致数值不稳定

## 建议的下一步

### 1. 进一步调试
- 检查产生 NaN 的具体节点和样本组合
- 分析 NaN 产生的根本原因（是输入问题还是计算问题）
- 验证 TensorRT 引擎构建的一致性

### 2. 可能的优化方向
- **更严格的输入验证**：在输入阶段就过滤异常值
- **更保守的 clamp 策略**：使用更小的安全范围
- **Kahan 求和**：对于累加操作，考虑使用 Kahan 求和算法（虽然当前使用 fmaf）

### 3. 验证策略
- **多次运行验证**：进行多次独立运行，统计平均成功率
- **特定案例调试**：针对产生 NaN 的特定节点/样本组合进行深入调试
- **FP32 基准对比**：确保 FP32 模式下 100% 成功，作为基准

## 代码变更总结

   - 修复输出指针计算
   - 增强数值稳定性检查

   - `getOutputDataType` 返回 FP32（当输入是 FP16 时）

3. **`SparseBox3DKeyPointsKernel.h`**
   - 添加 `outputFP32` 字段

4. **验证脚本**
   - 使用 FP32 参考实现进行比较

## 当前验证结果

### 多次运行统计（10 次运行）
- **成功率范围**：75%-95%
- **平均成功率**：约 85%
- **100% 成功率出现频率**：偶尔（约 10-20% 的运行）

### 失败模式
- **主要失败类型**：NaN 值
- **失败分布**：某些节点在特定样本上
- **失败频率**：不固定，存在随机性

## 结论

虽然已经实施了多项优化，但 FP16 精度的成功率仍未稳定达到 100%。这可能与：
1. TensorRT 引擎构建的随机性
2. CUDA 执行的并行性
3. 数值精度的边界情况

有关。需要进一步调试以找出根本原因。
